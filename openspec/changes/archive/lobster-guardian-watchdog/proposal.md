# 提案：OpenClaw 守护者 (Lobster Guardian)

## 1. 问题背景 (Problem)
- **配置脆弱性**：OpenClaw 的核心配置文件 `openclaw.json` 高度灵活，用户通过 Web 管理界面或聊天渠道（Channels）修改配置时，极易产生格式错误或逻辑冲突。
- **自杀式失联**：OpenClaw 的管理接口（Web UI 和 Channels）均运行在 `openclaw gateway` 进程中。一旦配置错误导致网关无法启动，这些管理接口也会随之失效。
- **修复成本高**：目前的恢复流程完全依赖于运维人员手动登录服务器，使用 CLI 命令行工具进行救治。
- **监控盲点**：当服务宕机或自愈发生时，运维人员无法在第一时间获取通知。

## 2. 解决方案 (Solution)
开发一个名为 **Lobster Guardian** 的独立守护进程（使用 Go 语言实现），作为“带外管理”哨兵运行：
- **独立生命周期**：不依赖 OpenClaw 运行状态，通过文件锁确保单例运行。
- **基于 CLI 驱动**：不调用 WebSocket API，而是通过 `os/exec` 直接调用 `openclaw` 命令。
- **多级自愈机制**：
    - **优先回滚**：自动从 `openclaw.json.bak` 恢复上一个稳定配置。
    - **深度修复**：若回滚失败，调用 `openclaw doctor --fix` 自动修复运行环境。
- **主动告警系统**：集成钉钉 Webhook，在探测到故障、尝试自愈及自愈成功时发送实时 Markdown 告警。

## 3. 核心目标 (Goals)
- [ ] **健康探测**：周期性通过 `openclaw health` 探测网关是否存活。
- [ ] **宕机诊断**：自动对比配置差异并生成 Markdown 故障报表。
- [ ] **自动回退与修复**：实现“配置回滚 -> 环境修复 -> 强制重启”的自愈闭环。
- [ ] **实时告警**：通过钉钉 Webhook 实现故障与恢复的即时通知。

## 4. 非目标 (Non-Goals)
- 不干预 OpenClaw 内部的 AI 决策逻辑。
- 不进行全量的数据备份。
